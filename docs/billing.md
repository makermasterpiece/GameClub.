# Stage 6: каталог, кошелёк и оплата игрового времени

Stage 8 добавляет продление по исходным billing snapshots и перенос без смены тарифа. Доплата пакета пропорциональна исходной цене/длительности; postpaid увеличивает резерв и лимит. Правила и API: [Stage 8](stage8.md).

Это описание минимального биллинга Stage 6 с management authorization, добавленной в Stage 7, а не заявление о готовности системы к промышленной эксплуатации. `api/admin/...` методы требуют Employee JWT и соответствующей policy и доступны также вне Development. Operator может читать данные, создавать игроков, пополнять кошелёк и управлять gaming sessions; Manager/Administrator дополнительно меняют каталог, баланс и статус игрока. Сотрудниками/enrollment управляет Administrator. Кассовые смены, продажи товаров и платёжные интеграции не реализованы. Development-сервер нельзя публиковать в недоверенную сеть.

## Модель и источник истины

`StationGroup` определяет группу компьютера. Миграция создаёт STANDARD, VIP и BOOTCAMP; новые станции относятся к STANDARD. Можно создавать собственные группы. Название обрезается по краям, ограничено 100 символами; уникальность группы проверяется по `NormalizedName` в верхнем регистре.

`Tariff` задаёт цену часа для одной группы. `TariffPackage` задаёт фиксированные цену и продолжительность, также для одной группы; у пакета может быть локальное окно доступности. Неактивные тарифы и пакеты нельзя покупать. Смена группы занятой станции запрещена.

Игровая сессия и авторизация игрока — разные сущности. Для покупки станция должна быть ONLINE, а игрок — иметь действующую авторизацию именно на этой станции. Одновременно у игрока и у станции может быть только одна активная/приостановленная игровая сессия. Наличие авторизации само по себе не означает покупку времени.

Server рассчитывает цену и время. Client не отправляет готовую стоимость и не авторизует продолжение игры локальным таймером. В сессию сохраняется снимок почасовой цены и параметров покупки: последующее изменение каталога не меняет уже купленную сессию.

## REST API

Каталог:

| Метод | Путь | Тело |
| --- | --- | --- |
| GET | `/api/admin/catalog` | Нет; возвращает `groups`, `tariffs`, `packages`, включая неактивные |
| POST | `/api/admin/catalog/groups` | `{ "name": "Training" }` |
| POST | `/api/admin/catalog/tariffs` | `{ "name": "Standard hourly", "stationGroupId": "GUID", "hourlyPrice": 600.00 }` |
| POST | `/api/admin/catalog/packages` | `{ "name": "Night", "stationGroupId": "GUID", "durationMinutes": 600, "price": 2500.00, "availableFrom": "22:00:00", "availableUntil": "08:00:00" }` |
| PUT | `/api/admin/catalog/tariffs/{id}/price` | `{ "price": 700.00 }` |
| PUT | `/api/admin/catalog/tariffs/{id}/active` | `{ "isActive": false }` |
| PUT | `/api/admin/catalog/packages/{id}/active` | `{ "isActive": false }` |
| PUT | `/api/admin/catalog/stations/{id}/group` | `{ "stationGroupId": "GUID" }` |

Для пакета без окна передайте оба поля `availableFrom` и `availableUntil` как `null`. Только одна граница или две одинаковые границы отвергаются. Цена пакета не изменяется отдельным endpoint: для новых условий создайте новый пакет и деактивируйте старый.

Кошелёк:

| Метод | Путь | Тело / результат |
| --- | --- | --- |
| GET | `/api/admin/users/{userId}/wallet` | `balance`, `reserved`, `available` |
| GET | `/api/admin/users/{userId}/wallet/transactions` | Последние 200 проводок, новые первыми |
| POST | `/api/admin/users/{userId}/wallet/deposit` | `{ "amount": 5000.00, "operationId": "NEW_GUID" }` |
| POST | `/api/admin/users/{userId}/wallet/adjustment` | `{ "amount": -100.00, "operationId": "NEW_GUID" }` |

Deposit должен быть положительным. Adjustment допускает положительное или отрицательное ненулевое изменение. Прямого API для установки `balance` нет. Каждое изменение записывает проводку с суммой, типом, итоговым балансом, временем UTC и ссылкой на операцию. Идентификатор сотрудника берётся из проверенной Employee identity, не из тела запроса.

Игровые сессии:

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/api/admin/gaming-sessions` | Создать оплаченную сессию; примеры ниже |
| POST | `/api/admin/gaming-sessions/{id}/pause` | Приостановить расход игрового времени |
| POST | `/api/admin/gaming-sessions/{id}/resume` | Продолжить неистёкшую сессию |
| POST | `/api/admin/gaming-sessions/{id}/end` | Завершить сессию и выполнить расчёт |
| GET | `/api/admin/gaming-sessions/{id}/events` | История изменений сессии |
| GET | `/api/agent/gaming/session/current` | Только HMAC-аутентифицированный Agent; станция берётся из удостоверенной identity |

Последний endpoint возвращает `{ "session": null, "serverTimeUtc": "..." }`, если действующей игровой сессии нет. Его нельзя вызывать от Client напрямую. SignalR-событие `GamingSessionChanged` содержит идентификатор станции и служит подсказкой Agent повторить HMAC HTTP-запрос, а не доверенным состоянием само по себе.

## Prepaid

Почасовая покупка:

```json
{
  "operationId": "NEW_GUID",
  "userId": "USER_GUID",
  "stationId": "STATION_GUID",
  "mode": "Prepaid",
  "tariffId": "TARIFF_GUID",
  "packageId": null,
  "purchasedMinutes": 90,
  "postpaidLimit": null
}
```

Цена равна `Round(hourlyPrice × purchasedMinutes / 60, 2)`. При цене 600 за час 90 минут стоят 900. Списание, создание сессии и событие старта входят в одну транзакцию: при недостатке доступных средств сессия не создаётся и списания не остаётся.

Для покупки пакета укажите `packageId`, а `tariffId` и `purchasedMinutes` оставьте `null`. Server определит длительность и спишет фиксированную `package.Price`. Одновременно выбирать тариф и пакет нельзя.

Входной предел продолжительности — 1–10080 минут. Это не означает, что любую такую длительность можно купить: дополнительно учитывается срок текущей авторизации игрока. Prepaid-покупка, эффективное окончание которой позже окончания авторизации, отклоняется до списания. Для длительной покупки требуется новая авторизация; её штатный срок — 12 часов с момента входа, а не с момента оплаты. Пауза не продлевает срок авторизации: после его истечения сессия завершается даже при наличии неиспользованных минут.

При досрочном завершении или logout автоматически возвращать неиспользованную часть prepaid-суммы система не будет. `FinalPrice` остаётся равной первоначальному списанию. Отдельный workflow возврата не реализован; наличие типа проводки `Refund` не означает наличие API возврата. Adjustment — отдельная ручная операция, а не автоматический возврат.

## Postpaid с резервом

```json
{
  "operationId": "NEW_GUID",
  "userId": "USER_GUID",
  "stationId": "STATION_GUID",
  "mode": "Postpaid",
  "tariffId": "TARIFF_GUID",
  "packageId": null,
  "purchasedMinutes": null,
  "postpaidLimit": 1200.00
}
```

Postpaid допускает только почасовой тариф. Сумма `postpaidLimit` резервируется, но при старте не списывается. Если лимит не указан, резервируется весь текущий доступный баланс. При недостатке средств покупка отвергается; резерв нельзя потратить повторно другой операцией.

`available = balance − сумма незакрытых резервов`. По умолчанию `Club:AllowNegativeBalance=false`: ни проводка, ни резерв не могут использовать больше доступных средств. Включение разрешения отрицательного баланса — отдельное явное изменение бизнес-политики, а не рекомендуемая настройка по умолчанию.

При `AllowNegativeBalance=true` prepaid/adjustment/итоговый postpaid charge могут увести баланс в минус, а явно заданный положительный `postpaidLimit` может зарезервировать больше имеющихся средств. Лимит суммы долга отдельно не реализован. Если `postpaidLimit` не задан и available не положителен, старт всё равно отклоняется: автоматического неограниченного времени в долг нет. Изменение этой настройки во время открытых резервов требует отдельной операционной оценки; штатный режим MVP — `false`.

Оплачиваемый предел времени рассчитывается в целых секундах: `floor(reserve / hourlyPrice × 3600)`, дополнительно ограничивается пределом модели и оставшимся сроком авторизации игрока. Если не обеспечена даже одна секунда, старт отклоняется. Изменение баланса после старта не продлевает уже определённый лимит времени автоматически.

При завершении резерв освобождается, а реальная стоимость прошедшего активного времени списывается одной проводкой `GamingCharge`. Остаток резерва снова становится доступным. Время паузы не оплачивается. Итоговая цена использует сохранённый тариф и накопленные ticks, затем один раз округляется до двух десятичных знаков.

## Денежная точность и повторы

Все денежные значения — `decimal`, хранение — `numeric(18,2)`. Пользовательские цены/суммы с дробной частью точнее 0.01 отвергаются, а не молча округляются. Каталожные цены должны быть положительными. Расчёт стоимости использует `MidpointRounding.AwayFromZero`: например, 1.005 становится 1.01. Минимальное обязательное списание отдельно не задано: очень маленькая рассчитанная стоимость может округлиться до 0.00.

Единица валюты в этой версии не хранится отдельным полем; смешивать разные валюты в одном развёртывании нельзя. Конвертация валют не реализована.

Для каждого нового пополнения, корректировки и покупки создавайте новый глобально уникальный `operationId`. При сетевом таймауте повторяйте исходный запрос с тем же ID и неизменным телом. Повторная покупка не списывает деньги заново; её ID также является ID игровой сессии. Повтор с изменёнными параметрами даёт `IDEMPOTENCY_CONFLICT`. Не переиспользуйте ID пополнения для покупки или другой операции.

Для повтора deposit/adjustment сохраняйте также ту же identity сотрудника: actor входит в проверку существующей проводки. ID postpaid-сессии резервируется для её будущего settlement и не может использоваться для стороннего пополнения даже до появления итоговой GamingCharge.

Завершение сессии также идемпотентно: postpaid-проводка привязана к ID сессии; уже завершённая сессия не рассчитывается повторно. Транзакции выполняются с PostgreSQL SERIALIZABLE и ограниченными повторами конфликтов. При исчерпании повторов возможна ошибка конфликта; клиент должен повторить именно первоначальную логическую операцию, сохранив `operationId`.

Каталожные операции не используют `operationId`. Повторное создание тарифа/пакета не следует считать идемпотентным.

## Окна пакетов и завершение

`Club:TimeZoneId` по умолчанию равен `UTC`. Для реального клуба явно задайте часовую зону, доступную ОС сервера, например `Club__TimeZoneId=Asia/Qyzylorda` для соответствующего клуба. Даты сессий и проводок сохраняются в UTC; `TimeOnly` окна пакета трактуется в локальном времени этой настроенной зоны, а не в часовом поясе браузера или Agent.

Начало окна включительно, окончание исключительно. Ночное окно 22:00–08:00 пересекает полночь. В 23:00 остаётся 540 минут; в 07:00 — 60 минут; в 08:00 покупка уже недоступна. Остаток округляется вниз до целой минуты и ограничивается фиксированной длительностью пакета. Если осталась только часть минуты, покупка отклоняется. Поздняя покупка не уменьшает фиксированную цену пакета: это условие нужно показывать до оплаты.

Окончание окна сохраняется отдельным абсолютным `WindowEndsAtUtc`. Пауза не переносит эту границу: пакет завершается в конце окна даже в состоянии Paused. При переходах DST несуществующая локальная граница отвергается; неоднозначная граница выбирается как наиболее ранний соответствующий момент UTC. Эти правила не позволяют продолжить ночной пакет после закрытия окна.

Server завершает сессию при исчерпании оплаченного времени, закрытии абсолютного окна, потере действующей авторизации игрока, явном `end` или logout. Background-проверка выполняется примерно раз в 5 секунд; текущий HMAC-запрос Agent также проверяет истечение. При задержке проверки оплачиваемое время ограничивается серверным deadline, а не временем обнаружения просрочки.

Завершение закрывает связанную авторизацию игрока. Agent возвращает Client в Available либо сохраняет более строгую базовую политику Locked/Maintenance. Нулевая цифра на Client не является командой завершения; Client ждёт подтверждения Server. При потере связи Agent/Client показывают Offline и не разрешают доступ на основании сохранённого кэша.

## Проверка изменений

Сначала примените все migrations, включая `AddTariffsAndWalletBilling`, `EnforcePackageWindowDeadline` и `AddEmployeeAdministrationAndClientHealth`, по инструкции README. Войдите сотрудником, создайте игрока, дождитесь ONLINE станции, разрешите вход и авторизуйте игрока. Через каталог узнайте группу станции, создайте соответствующий тариф, пополните кошелёк и выполните покупку с новым `operationId`. Во все административные REST-запросы добавляйте `Authorization: Bearer <employee-token>`.

Проверьте: повтор покупки не создаёт второго списания; изменение цены каталога не меняет купленную сессию; недостаток средств не оставляет частичной операции; postpaid-пауза не увеличивает стоимость; ранний prepaid-end не делает автоматический возврат; после end закрывается авторизация и изменяется состояние Client.

Автоматические проверки находятся в `tests/GameClub.Server.Tests/Billing` и интеграционных тестах PostgreSQL. InMemory-тесты проверяют правила и расчёты, но не заменяют PostgreSQL-проверки транзакций, уникальных ограничений и конкурентного списания. Точный результат последнего общего restore/build/test/migration gate фиксируется в отчёте текущего этапа, а не предполагается из наличия тестов.
