# Stage 10 — POS и смены сотрудников

## Реализованный объём

Категории, товары с ценой и целочисленным остатком, корзина, завершённая продажа со снимками строк, оплата кошельком либо учёт Cash/Card, полный возврат, открытие/закрытие собственной смены и её сводка. Это учётный POS внутри modular monolith; кассовый аппарат, эквайринг и фискальные документы не интегрированы. Stage 11–12 не реализованы.

Деньги используют decimal и точные два знака; цены должны быть положительными. Каталог ограничен 1000 товарами и 1000 категориями; остаток — 0..1 000 000, корзина — 1..100 различных товаров, количество строки — 1..1000. Неактивный товар или его категория запрещают новую продажу. Изменение каталога не меняет исторические название/цену/сумму SaleItem. После создания товара остаток изменяется отдельной операцией с причиной, а не полем редактирования метаданных.

## REST и права

Все маршруты имеют префикс `/api/admin/pos`, требуют Employee JWT и не доступны через Agent JWT. EmployeeId берётся из identity, а не JSON.

| Маршрут | Назначение / права |
| --- | --- |
| GET /catalog | Товары и категории; ClubRead |
| POST /categories; PUT /categories/{id} | Категория; ClubManageCatalog |
| POST /products; PUT /products/{id} | Товар; ClubManageCatalog, InitialStock при обновлении должен быть 0 |
| POST /products/{id}/stock | `{operationId, delta, reason}`; ClubManageCatalog |
| GET /shifts/current | Собственная открытая смена; ClubOperate |
| GET /shifts; GET /shifts/{id} | История / сводка; ClubRead, чужие доступны только с ClubManageMoney |
| POST /shifts | `{operationId, openingCash}`; ClubOperate |
| POST /shifts/{id}/close | `{operationId, closingCash}`; ClubOperate, только собственная смена |
| POST /sales | Корзина; ClubOperate, собственная открытая смена |
| GET /sales; GET /sales/{id} | Последние продажи / строки и возврат; ClubRead, чужие только с ClubManageMoney |
| POST /sales/{id}/refund | `{operationId, shiftId, reason}`; ClubManageMoney и собственная открытая смена |

Administrator/Manager управляют каталогом и возвратами; Operator может продавать и вести свою смену. История ограничена последними 50 сменами / 100 продажами. Новый SignalR event или Agent command для POS не добавляются; Agent/Client не участвуют в продаже.

Пример корзины (GUID заменить реальными; это не команда реального списания):

```json
{
  "operationId": "11111111-1111-4111-8111-111111111111",
  "shiftId": "22222222-2222-4222-8222-222222222222",
  "userId": null,
  "stationId": null,
  "paymentMethod": "Cash",
  "items": [{ "productId": "33333333-3333-4333-8333-333333333333", "quantity": 2 }],
  "expectedTotal": 500.00
}
```

Server рассчитывает цену сам. ExpectedTotal — необязательная проверка ожидаемой суммы: несовпадение даёт PRICE_CHANGED без продажи. Wallet требует активного игрока; StationId дополнительно требует действующего входа именно этого игрока на станции. Cash/Card без UserId допустимы. Нельзя передать произвольную цену строки, сотрудника или команду исполнения: неизвестные поля DTO отклоняются.

## Транзакции, возвраты и повторы

Продажа, строки, остатки/StockMovement, PosOperation, Payment либо WalletTransaction и аудит фиксируются одной SERIALIZABLE транзакцией. Нехватка товара или доступного кошелька откатывает всё. Wallet учитывает действующие резервы postpaid; покупка не может расходовать зарезервированную сумму. Cash/Card создают только внутреннюю Payment-запись: факт внешнего получения/возврата денег проверяет сотрудник клуба.

OperationId уникален для сценария и его fingerprint. Повтор того же запроса возвращает прежний результат; изменённое содержимое или использование ID другого POS/wallet/gaming действия отклоняется. При неизвестном сетевом результате повторяйте **тот же** OperationId и payload; новый ID означает новую операцию.

Возврат только полный, единственный на Sale, с обязательной причиной. Исходная продажа и строки не редактируются. Восстанавливаются все количества, кошельку возвращается историческая сумма либо создаётся отрицательный Cash/Card Payment. Возврат учитывается в текущей смене сотрудника, выполняющего возврат, даже если исходная смена уже закрыта. Если восстановление превышает допустимый остаток, возврат целиком отклоняется; произвольные частичные возвраты не поддержаны.

## Что означает сводка смены

Сотрудник имеет не более одной открытой смены. Продажи и возвраты запрещены в закрытую/чужую смену; закрытие не переписывает операции.

- ProductSales — валовая сумма продаж этой смены.
- Refunds — положительная сумма POS-возвратов, выполненных в этой смене.
- GamingSales — только отрицательные GamingCharge, записанные с EmployeeId этого сотрудника и CreatedAtUtc в интервале `[OpenedAtUtc, ClosedAtUtc)`, для открытой смены — до текущего времени.
- Cash/Card — продажи минус возвраты соответствующего метода этой смены; Wallet — аналогичная POS-сумма плюс GamingSales.
- ExpectedCash = OpeningCash + Cash; CashDifference = ClosingCash − ExpectedCash, до закрытия null.

Таким образом, Cash + Card + Wallet = ProductSales + GamingSales − Refunds. Возврат старой продажи может сделать текущий нетто-итог отрицательным. GamingSales **не является общей игровой выручкой клуба**: системные списания без сотрудника, другой сотрудник и проводки вне интервала исключены. При закрытии сохраняется GamingSalesSnapshot; поздний settlement не меняет эту закрытую цифру. Внесения кошелька не считаются повторно продажей. Stage 11 отчётность не заменяется этой узкой сводкой.

Игровое списание с EmployeeId читает открытую смену в своей транзакции. Вместе с чтением ledger и записью смены при закрытии это заставляет конфликтующие SERIALIZABLE-транзакции повториться: уже записанное внутри интервала списание не теряется из-за параллельного закрытия. Если после повтора списание проводится уже после закрытия, его новая дата находится вне старой смены.

## Схема, запуск и ключевые файлы

Миграция `20260908103342_AddPosProductsSalesAndEmployeeShifts` создаёт product_categories, products, employee_shifts, sales, sale_items, payments, sale_refunds, stock_movements, pos_operations. Внешние ключи Restrict сохраняют ссылки истории; unique partial index запрещает две открытые смены сотрудника. Не изменяйте ранее применённые migrations.

```powershell
dotnet restore GameClub.sln
dotnet build GameClub.sln --no-restore
dotnet ef database update --project src/GameClub.Infrastructure --startup-project src/GameClub.Server
pnpm --dir src/GameClub.Admin build
dotnet run --project src/GameClub.Server
```

Настройка PostgreSQL/HTTPS/секретов остаётся из README. Для Stage 10 обновляются Server и Admin после migration; существующие Agent/Client Stage 9 не получают нового протокола.

Ключевые файлы: `Domain/Pos/PosEntities.cs`, `Application/Pos/ProductCatalogService.cs`, `ShiftService.cs`, `PosSaleService.cs`, `Application/Billing/WalletService.cs`, `Infrastructure/Persistence/Configurations/PosConfiguration.cs`, `Server/Controllers/PosController.cs`. Корни путей — соответствующие проекты под `src/GameClub.*`.

## Ручная проверка на изолированной тестовой БД

1. Manager создаёт категорию, товар 125.50 с остатком 5. Operator не может изменить каталог, но видит товар.
2. Operator открывает смену с 100.00. Второе открытие запрещено; повтор исходного operationId не создаёт новую смену.
3. Продать 2 единицы Cash: итог 251.00, остаток 3, снимки строк и Payment сохранены. Повторить тот же запрос — остаток/суммы не изменяются второй раз.
4. Изменить цену в каталоге: старая продажа остаётся 251.00. Проверить PRICE_CHANGED при устаревшем ExpectedTotal новой корзины.
5. Проверить Wallet на тестовом игроке: одна ProductPurchase-проводка, отсутствие двойного списания. Нехватка денег, резервы postpaid, нехватка товара и неверный StationId не создают частичных записей.
6. Сделать Card-продажу только как тест учёта; не ожидать обращения к терминалу. Одновременно продать последний товар из двух запросов: успешен лишь допустимый по остатку объём.
7. Manager в собственной открытой смене делает полный возврат с причиной. Остаток восстановлен, историческая сумма возвращена, повтор не дублируется. Второй новый возврат и Operator-возврат запрещены.
8. Закрыть смену, сверить ExpectedCash/CashDifference. Повтор закрытия идемпотентен; новые продажи/возвраты в закрытую смену запрещены. Поздний возврат другой смены не переписывает её историю.
9. Сверить область GamingSales, исключая system EmployeeId=null; после закрытия snapshot стабилен. Не использовать сводку как общий бухгалтерский отчёт.
10. Проверить разграничение истории Operator/Manager и недопуск Agent JWT. Зафиксировать фактические результаты отдельно: наличие checklist не означает, что ручной сценарий уже пройден.

Фактически выполненные автоматические проверки фиксируются в [implementation report](implementation-report.md); real terminal/fiscal integration отсутствует по объёму этапа.
